# Card Pulse ロードマップ

> 状態: Active
>
> 最終更新: 2026-09-06

この文書は検証と開発の順序を示す。MVPの範囲と完了条件は [MVP定義](mvp.md) を正とする。日々の細かな作業管理を始めた後は、実行タスクをIssue等へ移し、この文書にはフェーズと判断条件を残す。

## Phase 0 — 対象と情報源を決める

- [ ] 候補となるTCGと店舗を [情報源マップ](../sources/source-map.md) に記録する。
- [ ] URL、形式、更新頻度、カード番号、状態条件、自動取得難易度を確認する。
- [ ] robots.txt、利用規約、アクセス制限、再利用条件、取得間隔を確認し、確認日と根拠URLを記録する。
- [ ] 代表サンプルを少量だけ確認し、カード識別子と価格条件を抽出できるか比較する。
- [ ] `1 TCG × 2〜3店舗` を選び、選定理由と見送った候補をADRに残す。

完了条件: 対象、情報源、取得間隔、利用上の制約が決まり、後続作業が未調査事項で停止しない。

## Phase 1 — 最小の開発基盤を作る

- [ ] Python、パッケージ管理、SQLite、migration手段の決定をADRに残す。
- [ ] `pyproject.toml`、lockfile、パッケージの最小構成を作る。
- [ ] setup、test、lint、format、型チェックの再現可能なコマンドを定義する。
- [ ] 設定、秘密情報、取得原本、ローカルDBの保存規則を整える。
- [ ] `run_id`、source、開始・終了時刻、取得件数、保存件数、エラー分類を記録するログを定義する。

完了条件: 新しい環境で文書どおりにセットアップし、空DB作成とテスト実行ができる。

## Phase 2 — データ契約と永続化を作る

- [ ] [データモデル](../architecture/data-model.md) を実データに合わせて確定する。
- [ ] [Collector契約](../contracts/collector.md) を型として実装する。
- [ ] 原本メタデータと価格観測値の追記型保存を実装する。
- [ ] content hash、情報源内ID、観測値の重複防止規則を決める。
- [ ] 欠損、不正金額、重複、再解析、rollbackのテストを作る。

完了条件: 固定JSON/CSVサンプルを投入し、追跡可能で重複のない観測値を再現できる。

## Phase 3 — Web Collectorを縦に通す

- [ ] 最も構造化された情報源で、取得、原本保存、解析、同定、DB保存まで実装する。
- [ ] User-Agent、timeout、低頻度アクセス、backoff、最大再試行をsource設定として定義する。
- [ ] 保存が許される固定fixtureを用意し、ネットワークなしでparserをテストする。
- [ ] 0件、必須項目欠損、件数急減を正常終了にしない検知を作る。
- [ ] 2つ目、3つ目の情報源を追加し、共通契約を見直す。

完了条件: 2〜3店舗のデータが同じ観測モデルに入り、一つの失敗が他へ波及しない。

## Phase 4 — カード同定と相場照会を作る

- [ ] TCG、セット、カード番号、レアリティ、版、言語による同定規則を検証する。
- [ ] 原文表記、正規化表記、別名、同定状態を保存する。
- [ ] 完全一致、自動候補、レビュー必須、未同定を区別する。
- [ ] 最新価格、中央値、最高値、最低値、店舗数、鮮度、スプレッドを計算する。
- [ ] 集計値と根拠観測をCLIまたはJSONで確認できるようにする。

完了条件: 代表カードについて、根拠付きの店舗比較と履歴を再現できる。

## Phase 5 — 試験運用して価値を判定する

- [ ] 低頻度の増分取得を2〜4週間実行する。
- [ ] 成功率、重複率、未同定率、レビュー時間、parser変更を記録する。
- [ ] 仕入れまたは売却判断に役立った事例を [Experiments](../experiments/README.md) に記録する。
- [ ] 古い価格が新しい価格として表示されないことを確認する。
- [ ] バックアップと空環境への復元を実施する。
- [ ] 継続、対象変更、中止の判断をADRに残す。

完了条件: 利用価値、維持時間、データ品質を数値と事例で説明できる。

## Phase 6 — 手動画像取込とOCRを検証する

構造化Webだけでは不足すると判明した場合に進む。

- [ ] 画像、店舗、URL、公開日時を一緒に受け取る手動取込を作る。
- [ ] 原画像を先に保存し、OCR結果を派生データとして残す。
- [ ] 項目単位のconfidenceとreview queueを実装する。
- [ ] 誤認識率と1枚あたりのレビュー時間を測る。

完了条件: 人間の修正時間を含め、手入力より有利か判断できる。

## Phase 7 — X取得を判断する

X限定情報の利益が取得・保守コストを上回る場合だけ進む。

- [ ] Webとの重複率、X限定情報数、判断への寄与、月間件数を測る。
- [ ] 公式APIの料金、rate limit、利用規約をその時点で再確認する。
- [ ] 公式API、手動取込、非公式取得の費用・規約・停止リスク・保守時間を比較してADRに残す。
- [ ] X固有コードを交換可能なsource adapter内に閉じ込める。
- [ ] 取得停止後も保存済みデータと他の機能を利用できることを確認する。

完了条件: 採用理由、運用制約、撤退条件が明文化されている。

## Phase 8 — Card Diggerと連携する

相場データの有用性を確認した後に進む。

- [ ] Card Diggerのユースケースから必要な問い合わせを定義する。
- [ ] カード識別子、曖昧一致、鮮度、欠損時の応答を決める。
- [ ] 同一プロセスまたはファイル出力で契約を検証し、必要ならHTTP API化する。
- [ ] 中央値、店舗数、鮮度、ばらつき、根拠観測を返す。

完了条件: Card Diggerが内部DBへ依存せず、根拠付き価格情報を取得できる。
