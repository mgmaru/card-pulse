# ADR-0007: 情報源を分けず、処理段階で構造化データを分離する

- 状態: Accepted
- 日付: 2026-09-09
- 決定者: プロジェクトオーナー
- 置換するADR: なし
- 置換されたADR: なし

## Context

Card Pulseが扱うHTML、JSON、CSV、画像等は、取得できる項目と確からしさが異なる。構造化Webではカード番号や価格を直接抽出できても、画像ではOCRの誤認識、表構造の復元失敗、版やレアリティの欠損が起こり得る。取得時点の不完全なデータへ確定価格と同じ必須項目を求めると、後から再処理できる証拠を失う。

一方、情報源ごとにDBを分けても、不足項目は補われない。店舗横断の価格比較には、最終的に各情報源のデータを共通の`card_identity`、`shop`、価格条件へ対応付ける統合処理が必要になる。DBを分けると、同定、重複排除、review、migration、backup、集計queryをDB間で調整する負担が加わる。

[ADR-0004](0004-server-database-selection.md)は構造化データのsystem of recordをサーバー側DBへ置き、原本本体をartifact storageへ分けると決定している。ただし、原本から確定した価格観測に至る途中の解析結果、欠損候補、同定試行をどのように保持するかは決めていなかった。

## Decision

- 情報源横断の構造化データは、一つの論理的なsystem of recordで管理する。取得項目や形式の違いだけを理由に、情報源ごとのDBを作らない。
- HTML、JSON、CSV、PDF、画像等の原本本体はartifact storageに保存し、DBには原本メタデータと後続処理への参照を持たせる。
- 原本から比較に使える価格観測までを、次の論理段階に分ける。
  1. `raw_artifact`: 取得した原本と取得メタデータ
  2. `processing_run`: parser、OCR等を原本へ適用した実行記録
  3. `extracted_record`: 原本から抽出した欠損可能な行または項目
  4. `observation_candidate`: 価格候補として最低限の検証を通過した記録
  5. `identity_resolution_attempt`: 内部カードとの照合候補、根拠、結果
  6. `price_observation`または`review_item`: 確定観測、または人間の判断を待つ記録
- 各段階は論理的な責務の境界とする。実装時に一段階を複数tableへ分けるか、同じtransactionで複数段階を保存するかは、[データモデル](../architecture/data-model.md)とmigrationで決める。
- `extracted_record`は業務上の必須項目が欠けていても保存できるようにする。欠損、不正値、警告を保持し、原本へ戻って再処理できるようにする。
- 原本、source metadata、取込設定、正規化処理、人間の判断のどこから値を得たかを追跡する。取込設定等から値を与える場合も、原本から直接抽出した値として扱わない。
- OCR等の抽出confidenceと、カード同定のmatch scoreを別の値として扱う。一方の高さを他方の確定根拠にしない。
- `price_observation`には、金額、通貨、価格種別、shop、TCG、取得日時、原本への追跡可能性と、確定したカード同定を要求する。条件を満たさない結果は確定観測へ昇格させない。
- 原本、処理実行、抽出結果、同定試行、review判断、確定観測を追記型で保持する。再解析と訂正では以前の結果を上書きしない。
- この判断は将来の画像入力にも適用できるデータ境界を定めるが、画像OCRとX取得をMVPへ追加しない。実施時期は[MVP定義](../product/mvp.md)と[ロードマップ](../product/roadmap.md)に従う。
- 法的な保持・削除条件、アクセス制御、データ所在地、負荷または運用責任が情報源ごとに明確に異なる場合は、artifact storageまたは構造化データの物理分離を再検討し、新しいADRで判断する。

## Consequences

- 欠損した画像解析結果も失わずに保存し、OCRやparserの改善後に同じ原本から再処理できる。
- `card_identity`、review結果、重複防止規則、店舗横断集計を一つの論理データモデルで扱える。
- source固有の項目は抽出結果と由来情報に残し、確定観測のschemaへsource固有列を増やさずに済む。
- 中間結果、状態遷移、派生関係を保存するため、直接`price_observation`だけを保存する構成よりtable数、保存量、queryが増える。
- OCRの精度とカード同定の精度は別々に検証する必要があり、曖昧な結果には人間のreview時間が発生する。
- DBを共有してもsourceごとの障害が自動的に隔離されるわけではないため、取込実行、queue、transaction、権限、監視をsource単位で管理する必要がある。
- 情報源の利用条件によって原本を保存できない場合、DB分割では解決しない。その情報源を採用するには、現在のprovenance要件と両立する許諾または代替証拠が必要になる。

## Alternatives considered

- 情報源ごとにDBを分ける: 入力schemaを独立させやすいが、比較時に共通カード同定と価格条件へ統合する必要があり、問題がDB間処理へ移る。MVPの規模ではmigration、backup、監視の増加に見合う根拠がない。
- 不完全な候補も`price_observation`へ保存する: tableは少なくなるが、未同定や不正な価格が相場queryへ混入しやすく、確定観測の意味が曖昧になる。
- 解析結果を保存せず、原本から毎回直接`price_observation`を生成する: 実装は短いが、どの値が欠損・誤認識したか、どの同定規則を使ったかを比較できず、reviewと再解析の再現性を失う。
- すべての情報を一つの自由形式payloadへ保存する: source差は格納できるが、確定観測の制約、重複防止、横断queryを保証しにくい。

## Validation

- `CP-0004`で代表サンプルごとに、原本から直接抽出する値、source metadataまたは取込設定から得る値、欠損可能な値、同定に必要な値を区別する。
- `CP-0016`と`CP-0017`で中間段階の意味と契約を実データに合わせ、`CP-0066`で追記型保存と原本からの追跡を実装する。
- 許諾済みfixtureと、保存・再利用可能な合成またはsanitized画像候補を使い、欠損した`extracted_record`、候補への昇格、review、再解析を再現する。
- Phase 5とPhase 6で未同定率、誤同定率、項目別抽出精度、review時間、保存量を測る。
- 情報源ごとに異なる保持・アクセス条件または実測上の負荷が発生した場合、物理分離の費用と効果を再評価する。
