# ADR-0008: カード同定には意味を持たない内部UUIDを使う

- 状態: Accepted
- 日付: 2026-09-09
- 決定者: プロジェクトオーナー
- 置換するADR: なし
- 置換されたADR: なし

## Context

Card Pulseは、複数の情報源にある価格を同じカードへ対応付ける必要がある。情報源内の商品IDは発行元ごとに異なり、カード単位のIDを持たない情報源もある。カード番号、セット、レアリティ、版、言語等は横断照合に使える一方、欠損、表記揺れ、後から判明する版差分を含む。

`CP-0002`の調査でも、[遊々亭](../sources/yuyutei.md#データ形式)は店舗固有のset codeとcard IDを持つ一方、[ドラゴンスター](../sources/dragonstar.md#データ形式)の`PN`には異なるカード間の重複があり、[フルコンプ](../sources/fullcomp.md#データ形式)ではカード単位のIDを確認できなかった。いずれか一つの値を情報源横断のカード主キーにすることはできない。

カード属性を連結した`SV8a-236/187-UR`のような値を主キーにすると、その属性を完全かつ不変と仮定することになる。実際には同じカード番号とレアリティでも、言語、初版、加工、スタンプ等によって市場で別のカードとして扱う場合がある。後から差分が判明すると、一意制約により本来別のカードを追加できない、既存行を上書きする、または主キーと参照先を変更する必要が生じる。

一方、意味を持たないIDだけでは誤同定を防げない。誤りを訂正するには、観測候補、同定試行、確定観測、原本を個別に識別し、どの根拠でどの内部カードへ対応付けたかを履歴として残す必要がある。[ADR-0002](0002-append-only-provenance.md)の追記型保存と[ADR-0007](0007-layered-ingestion-data.md)の処理段階を、カードの内部識別にも適用する。

## Decision

- `card_identity`は、価格比較で区別する同じ印刷仕様のカードを表す。個々の所有物や、同名・同効果のカードをまとめた概念は表さない。
- `card_identity`の主キー`card_identity_id`には、Card Pulseが発行する衝突耐性のあるUUIDを使う。TCG、セット、カード番号、レアリティ、版、言語、情報源等の業務上の意味を埋め込まない。
- UUIDは一度発行したら変更しない。API等へ公開する場合もopaqueな値として扱い、利用側は値の一部からカード属性や作成順を解釈しない。UUIDのversionと生成libraryはPython・DB選定後に決める。
- TCG、セット、カード番号、レアリティ、版、言語、加工、スタンプ等は、カード同定、検索、重複候補の検出に使う属性として保持する。対象TCGで自動同定に必要な組合せは代表サンプルで検証し、これらを主キーにはしない。
- カード名、店舗、価格、取得日時、状態、鑑定gradeは`card_identity_id`へ含めない。状態と鑑定gradeは価格観測側の条件として扱う。
- 公式マスタや店舗が発行するIDは内部主キーにせず、namespace、外部ID、対応する`card_identity_id`、根拠を持つ`card_external_reference`として管理する。外部IDが複数カードをまとめる場合や一意性・安定性を確認できない場合は、確定した外部参照に昇格させず原本または観測候補の値として残す。
- 同定の誤りが判明した場合は、必要な`card_identity`を追加し、新しい`identity_resolution_attempt`と訂正、無効化または置換関係を記録する。以前の同定試行、価格観測、原本を上書きまたは削除しない。
- 同じ印刷仕様へ複数の内部UUIDを発行した場合も、一方の主キーへ値を付け替えて履歴を消すのではなく、統合または置換関係と判断根拠を残す。分割・統合の具体的なschemaはデータモデルとmigrationで定める。
- `source_item_id`、原本の重複防止キー、価格観測の重複防止キーは`card_identity_id`と別に定義する。一つの値をカード同定と取込の冪等性へ兼用しない。

例えば、当初`SV8a + 236/187 + UR`だけを根拠に通常版と別加工版を同じ`card_identity_id = A`へ対応付けた後、別仕様だと判明した場合を考える。Card Pulseは別の`card_identity_id = B`を発行し、誤ってAへ対応付けた候補について、旧判断を残したままBを選ぶ新しい同定試行と訂正関係を追加できる。`SV8a-236/187-UR`自体が主キーであればBを登録できないか、既存のキーを変更する必要がある。

## Consequences

- カード属性の訂正や新しい版差分の発見があっても、既存の内部参照を壊さずにカードを分割、統合、訂正できる。
- 一つの店舗のID変更、欠損、廃止から内部カードの身元を分離し、複数情報源を同じ内部カードへ対応付けられる。
- APIはカード属性の命名規則を識別子へ固定せず、後方互換なopaque IDを提供できる。
- UUID自体は誤同定や重複登録を防がないため、属性による候補検出、外部参照、同定規則、review、分割・統合履歴が必要になる。
- 人がUUIDを見てもカードを判別できないため、運用画面とログでは正規化名、セット、カード番号等を併記する必要がある。
- 自然キーだけを使う構成より、外部参照と訂正関係の保存、現在有効な対応を選ぶqueryが増える。

## Alternatives considered

- セット、カード番号、レアリティ等を連結した自然キーを使う: 人が読みやすく重複を抑えやすいが、欠損や版差分の発見でキーの意味が変わり、誤結合の分割と参照の維持が難しい。
- 属性のhashを主キーに使う: 固定長で決定的に生成できるが、元になる属性の訂正や正規化規則の変更でhashが変わるため、自然キーと同じ結合を持つ。
- 一つの店舗または公式マスタのIDを内部主キーに使う: 取得元では便利だが、提供終了、ID変更、網羅範囲、利用条件へ内部モデルが依存し、別情報源だけに存在するカードを扱えない。
- DBの自動採番整数を使う: 意味を持たない主キーとして訂正には対応できるが、手動取込、環境間のデータ移送、将来の複数生成経路で採番主体をDBへ集中させる。Card Pulseでは生成場所をDB製品から分離できるUUIDを採用する。

## Validation

- `CP-0004`で、通常版と版違い、番号またはセット欠損、言語違い等を含む代表サンプルを比較し、属性の組合せによる衝突と未同定を確認する。
- `CP-0016`で`card_identity_id`、`card_external_reference`、分割・統合・置換関係の具体的なschemaと制約を定める。
- `CP-0019`で原本と観測の重複防止キーが`card_identity_id`から独立していることを確認する。
- `CP-0029`から`CP-0031`で、完全一致、候補、review、未同定の境界を検証する。
- 誤って二つの版を統合したケースと、同じ版へ二つのUUIDを発行したケースをtestし、旧判断と原本を保持したまま訂正結果を得られることを確認する。
