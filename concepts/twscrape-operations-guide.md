# twscrape 運用ガイド

> **目的**: 個人利用を前提に、twscrape を使って X からデータを取得するにあたっての判断根拠・リスク・設計方針・メンテナンス手順をまとめたもの。
> **作成日**: 2026-09-04
> **対象バージョン**: twscrape 0.20.1（2026-08-25 リリース）

---

## 1. 結論サマリ

| 項目 | 判断 |
| --- | --- |
| 採用可否 | **採用する**（個人利用、非商用、小規模に限る） |
| 最大のリスク | X の仕様変更による突然の機能停止（緩和不能） |
| 次点のリスク | 上流リポジトリの消失（緩和可能） |
| 必須の対策 | ①独立リポジトリへのミラー ②ロックファイルによる固定 ③取得と利用の分離 |
| 撤退判断の指標 | **1回の障害修正にかかる時間** |
| やってはいけないこと | メインアカウントの使用、アカウントの購入、Fork ボタンでのバックアップ |

## 2. twscrape とは

- **リポジトリ**: `vladkens/twscrape`（MIT ライセンス、GitHub 2.7k stars）
- **方式**: 公式 API ではなく、**認証済みアカウントの Cookie を使って X の内部 GraphQL エンドポイントを叩く**
- **言語**: Python（async/await ベース）

### 主な機能

| カテゴリ | 内容 |
| --- | --- |
| 検索 | ツイート検索（Latest / Top / Media）、ユーザー検索、トレンド検索 |
| ツイート | 詳細、リプライ、スレッド全体、リツイートしたユーザー、ブックマーク |
| ユーザー | プロフィール、フォロー / フォロワー、認証済みフォロワー、投稿 / リプライ / メディア |
| リスト | タイムライン、メンバー |
| コミュニティ | 情報、メンバー、モデレーター、投稿 |

### 運用上ありがたい設計

- **アカウントプール**: レートリミットをアカウント単位・エンドポイント単位で追跡し、制限に掛かったら自動で別アカウントに切り替え
- **2種類の出力**: パース済みモデル（SNScrape 互換）と生のレスポンス（`_raw` 版）の両方
- **セッション永続化**: SQLite に保存
- **プロキシ対応**: アカウント単位で設定可能
- **CLI**: JSON Lines 出力なのでパイプ処理しやすい
- **curl-cffi バックエンド**（任意）: ブラウザ的な TLS フィンガープリント

### 既知の制約

- `limit` はページサイズではなく **取得目標件数**
- `user_tweets` 系は X 側の制約で **約 3,200 件が上限**
- 匿名テレメトリがデフォルト有効 → `TWS_TELEMETRY=0` で無効化

### メンテナンス状況（2026-09 時点）

```
0.17.0 ──── (1年以上の空白) ──── 0.18.0 ── 0.19.0 ── 0.19.2 ── 0.20.0 ── 0.20.1
2025-04                          2026-05   2026-06   2026-07   2026-08   2026-08-25
                                 ↑
                                 X の変更後にスクレイピング互換性を復旧
```

- 直近はほぼ **月次リリース**。良好。
- ただし **1年以上リリースが止まった実績がある**（メンテナは1人）。
- 直近3リリースすべてに「GraphQL operation ID を現行の X API に合わせて更新」が含まれる
  → **X 側の変更を追い続けないと壊れる性質のライブラリ**

## 3. リスクの3層構造

リスクは性質の異なる3つに分解できる。**それぞれ対策が違う**ため、まとめて考えないこと。

```
┌─────────────────────────────────────────────────────────┐
│  (3) 法務リスク                                          │
│      X からの停止通告でリポジトリ / PyPI が消える         │
│      → 緩和可能（ローカル確保）                           │
├─────────────────────────────────────────────────────────┤
│  (2) 技術的対抗リスク                          ★最重要   │
│      x-client-transaction-id / operation ID の変更       │
│      → 緩和不能。壊れる前提で設計するしかない             │
├─────────────────────────────────────────────────────────┤
│  (1) メンテナ依存リスク                                  │
│      作者が飽きる・忙しくなる                             │
│      → 緩和可能（抽象化・バージョン固定・自前メンテ）      │
└─────────────────────────────────────────────────────────┘
```

| リスク | 発生確率 | 緩和可否 | 対策 |
| --- | --- | --- | --- |
| (1) メンテナ依存 | 中（実績あり） | ○ | 抽象化レイヤ、バージョン固定、最終的には自前メンテ |
| (2) 技術的対抗 | **高（2〜4週間周期）** | **×** | 壊れる前提の設計。データを溜めて再取得しない |
| (3) 法務 | 低〜中 | ○ | 独立リポジトリへのミラー |

### (2) について: なぜ X は仕様を変えるのか

**アンチボット機構の「存在」は意図的、「変更頻度」は主に開発の副産物。**

- `x-client-transaction-id` は、ホームページの SVG アニメーション座標と `ondemand.s.js` のキーバイトを組み合わせて署名を生成する仕組み。
  → **機能的に必要な処理は1つもなく、「ブラウザが実際に JS を実行した」ことを証明させるためだけに存在する** = 明確なアンチボット機構
- ただしその標的は **スパム / 大規模データ収集 / 商用スクレイパー / 攻撃** であって、OSS ライブラリや個人利用は**巻き添え**。名指しの標的ではない。
- 一方、2〜4週間ごとの破壊は主に通常開発の副産物:
  - GraphQL operation ID = persisted query のハッシュ → フィールドを1つ足せば変わる
  - webpack チャンク名 = コンテンツハッシュ → デプロイのたびに変わる
- **根拠**: 修正が15〜30分で済む定型作業に留まっている。本気で潰しに来ているなら、意味論を変える難読化や挙動検知に踏み込むはず。

> **悪意ではなく無関心が原因。** だからこそ予告なく、交渉の余地もなく壊れる。

### (3) について: Nitter との比較

2026-08-24、X Corp. が Nitter に停止通告を送付。nitter.net と XCancel は停止、リポジトリはアーカイブされた。

| 観点 | Nitter | twscrape |
| --- | --- | --- |
| 形態 | 公開インスタンスを運営するサービス | ライブラリ（稼働していない） |
| ランハム法（商標）の適用 | ○ X の代替フロントエンドを提供 | × 該当しない |
| スクレイピング自体の指摘 | ○ | ○（同様に該当しうる） |
| 可視性 | 高（公開 URL、13.5k stars） | 中（2.7k stars） |
| **固有の弱点** | — | **README にアカウント売買業者へのアフィリエイトリンク** |

- twscrape のほうが**構造的には狙われにくい**が、ゼロではない。
- アフィリエイトリンクは「中立的な技術ツール」という立場を弱める要因。ただし**これは利用者側のリスクではなくプロジェクト存続のリスク**。自分でアカウントを作れば利用者には無関係。

> ※ 法的評価ではなく構造の比較です。実際の判断が必要な場合は専門家に確認してください。

## 4. 設計方針

X からの依存は原理的に消せない。目指すのは**依存が切れたときの被害範囲を小さくすること**。

### 原則1: 取得と利用を分離する

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   X (敵対的)  │ ──▶ │  取得レイヤ   │ ──▶ │ ローカル DB   │
│              │     │  (捨てレイヤ) │     │  (資産)      │
└──────────────┘     └──────────────┘     └──────┬───────┘
                       ↑ いつ死んでもいい          │
                       twscrape はここに閉じ込める │
                                                  ▼
                                          ┌──────────────┐
                                          │  利用レイヤ   │
                                          │ ここだけを見る │
                                          └──────────────┘
```

- twscrape への依存を**取得レイヤ1箇所に閉じ込める**
- 利用側は「ローカルに溜まったデータ」しか見ない
- 取得が死んでも、止まるのは新規取得だけ。既存の成果物は生き残る

### 原則2: 取ったら保存し、二度と取り直さない

- 「毎回 API から取ってきて表示する」構造は**取得が死んだ瞬間に価値がゼロになる**
- 一度取ったものは必ずローカルに永続化し、以降はそこを参照
- 取得は**増分のみ**

### 原則3: X が明日ゼロになっても価値が残るものだけ作る

- 「X のデータが継続的に入ってくること」を前提にした仕組みは作らない

### 原則4: 取得頻度は可能な限り下げる

- 取得頻度 = 壊れて気づく回数 = 対処コスト
- 例: 「1日1回、特定アカウントの新規投稿だけ」なら、数日壊れていても実害はほぼない
- **リアルタイム性が必要な用途なら、この構成自体が向いていない**

## 5. 利用時のルール

### 必須

| ルール | 理由 |
| --- | --- |
| **メインアカウントを使わない** | 規約違反による凍結リスク。捨てアカウントを自分で作る |
| **アカウントを購入しない** | 規約違反 + 何が仕込まれているか不明（セキュリティ的に論外） |
| **取得間隔に余裕を持たせる** | 検知を避ける。急ぐ理由がない |
| **取得したデータは保存し再取得しない** | 上記の設計原則 |
| **`TWS_TELEMETRY=0`** | 匿名テレメトリの無効化（任意だが推奨） |

### 認証について

- 最も安定するのは、ブラウザの Cookie（`auth_token` と `ct0`）を登録する方法
- 認証情報はローカルの SQLite に保存される → **DB ファイルの管理に注意**
- README 自身が「X の利用規約は複数アカウントの使用を推奨していない。自己責任で節度を持って使うこと」と明記

## 6. ローカル確保（バックアップ）手順

### 6.1 なぜ必要か

| 守れるリスク | 守れないリスク |
| --- | --- |
| 上流リポジトリの消失 | X の仕様変更による機能停止 |
| PyPI からの削除 | （これは何をしても守れない） |

> **ローカル確保が守るのは「入手できなくなること」だけ。「壊れること」は守れない。**

### 6.2 ⚠️ Fork ボタンを使ってはいけない

```
❌ GitHub の Fork ボタン
   → fork network に属する
   → 上流が takedown されるとネットワークごと無効化されうる
   → 保険にならない。むしろ運命共同体になる

✅ git clone → 新規リポジトリとして push
   → fork network に属さない
   → 上流が消えても独立して生き残る
```

### 6.3 手順

```bash
# 1. 完全な複製（全ブランチ・全タグ・全履歴）
git clone --mirror https://github.com/vladkens/twscrape.git
cd twscrape.git

# 2. 自分の Private リポジトリを remote に追加して push
git remote add mine git@github.com:<自分>/twscrape-mirror.git
git push --mirror mine
```

- **Private リポジトリで十分**。NAS やセルフホストは必須ではない
- リポジトリ名は自由。**私的な保管に商標・著作権上の問題はない**
- MIT ライセンスにより複製は明示的に許諾されている。**上流が消えてもこの許諾は取り消されない**

### 6.4 定期同期

```bash
git remote update          # 上流の変更を取り込む
git push --mirror mine     # 自分のリポジトリに反映
```

- 手作業なら **月1回・1分未満**
- GitHub Actions の cron で自動化するのが現実的（作るのは1回だけ）
- **同期が滞っても気にしなくてよい**。目的は保険であって最新への追従ではない。1年古くても「動くコードベースと履歴」があればゼロからの解析とは天と地の差

### 6.5 wheel は不要

| 対象 | 保存の要否 | 理由 |
| --- | --- | --- |
| 依存パッケージ（httpx 等）の wheel | **不要** | PyPI から削除される確率は実質ゼロ。ロックファイルで足りる |
| twscrape 本体の wheel | **不要** | `git clone` 済みなので `pip install .` でよい |
| ロックファイル | **必須** | ← これが本命 |

- yank（取り下げ）は**ロックファイルで守れる**。厳密にバージョン指定されていればインストール可能
- ロックファイルで守れないのは **完全削除**だけ。その対象は twscrape 本体のみで、すでに clone で確保済み
- オフライン運用が必要な場合のみ `pip download twscrape -d ./vendor` を検討

### 6.6 ロックファイルの品質

wheel を貯めるより、こちらが重要。

- [ ] バージョンが厳密に固定されている（`==`、または `uv.lock` / `poetry.lock`）
- [ ] ハッシュが含まれている（`--require-hashes` が効く状態）
- [ ] transitive な依存まで全部載っている

## 7. 障害対応とメンテナンス

### 7.1 壊れ方の種類と対処コスト

| 壊れ方 | 症状の例 | 自力対応 | 目安 |
| --- | --- | --- | --- |
| **operation ID の変更** | 特定エンドポイントだけ 404 / エラー | ○ 可能 | 15〜30分 |
| **バンドル構造の変更** | `Couldn't get KEY_BYTE indices` 等 | △ 正規表現の追従なら可能 | 15〜30分〜 |
| **署名アルゴリズム自体の変更** | 全リクエストが失敗 | ✕ 個人には重い | 数日〜 |

### 7.2 上流が死んだ場合の移行手順

```
段階1（現在）: 上流をそのまま使う
  ├─ ロックファイルで twscrape==0.20.1 を固定
  ├─ Private リポジトリにミラー（月1同期）
  └─ 上流が生きている限りミラーは一度も使わない

        ↓ 上流が消えた / 壊れて自分で直す必要が出た

段階2: 参照先を自分のリポジトリに切り替える
  ├─ 依存指定を Git URL またはローカルパスに変更
  ├─ この時点で PyPI への依存が消える
  └─ 以降は自分のメンテナンス範囲
```

- 段階2に入っても、**ゼロから解析する必要はない**
- `x-client-transaction-id` の生成は複数の独立実装が公開されている
  - `iSarabjitDhiman/XClientTransaction`（Python、事実上の参照実装）
  - `fa0311/twitter-tid-deobf-fork`（毎日 UTC 22:00 に自動で難読化解除を実行）
  - `fa0311/TwitterInternalAPIDocument`（X の内部 API を日次で自動ドキュメント化。operation ID もここから取れる）
- **知識は分散して生き残る**。twikit 本家が半年放置された結果フォークが3つ生えたのと同じことが起きる

### 7.3 撤退判断の指標

> ### 🔍 **監視すべきは「1回の障害修正にかかっている時間」**

```
現在: 15〜30分の定型作業  ──────────▶  正常。X はこちらを見ていない

もし:  数日〜数週間かかるようになった
      changelog に「難読化に対応」「新しい challenge に対応」が出始めた
                          │
                          ▼
              X がアンチボット機構を本格的に強化した合図
              = 撤退または方針転換の判断ポイント
```

- スター数でもリリース頻度でもなく、**修正の難易度**が先行指標

## 8. 代替手段（並行して検討する価値があるもの）

| 手段 | 特徴 | 向いている用途 |
| --- | --- | --- |
| **X 公式のデータエクスポート** | 規約上クリーン、労力ゼロ | 自分の投稿・ブックマーク・DM が対象なら**これで足りる** |
| **X のリスト機能** | 規約上クリーン | 特定アカウント群を眺めたいだけなら |
| **Rettiwt-API** | TypeScript、**ゲスト認証でログイン不要**（ツイート詳細・ユーザー詳細・タイムラインに限る） | 凍結リスクを完全に避けたい場合 |
| **X 公式 API** | 従量課金（無料枠は2026-02に新規向け終了） | 規約遵守が必須な場合。要コスト試算 |
| **Bluesky (AT Protocol)** | **完全にオープン**。申請・審査・API キー不要。公開データの読み取り無料 | 技術系の情報収集なら相当カバーできる |

> **敵対的でないソースに同じ労力を投じたほうがリターンが大きい**、という視点は常に持っておく。
> twscrape のメンテを追う労力と、AT Protocol を素直に叩く労力では後者が圧倒的に軽く、しかも壊れない。

## 9. チェックリスト

### 導入時（1回だけ）

- [ ] 専用のアカウントを**自分で**作成する（メインアカウントは使わない）
- [ ] Cookie（`auth_token`, `ct0`）を取得して登録
- [ ] `TWS_TELEMETRY=0` を設定
- [ ] `git clone --mirror` → Private リポジトリに push（**Fork ボタンは使わない**）
- [ ] ロックファイルでバージョン + ハッシュを固定
- [ ] 取得レイヤと利用レイヤを分離した構成にする
- [ ] ローカル永続化の仕組みを先に作る（取得より先に）

### 定期（月1回程度）

- [ ] ミラーリポジトリの同期（Actions で自動化推奨）
- [ ] 上流の changelog を確認 → **修正にかかった時間の傾向**をチェック

### 障害時

- [ ] 上流に同じ症状の issue が上がっていないか確認
- [ ] 上流が対応済みならバージョンを上げる
- [ ] 上流が停止している場合、フォークが出ていないか確認
- [ ] 自力対応する場合、`XClientTransaction` / `TwitterInternalAPIDocument` を参照

## 付録: 用語メモ

| 用語 | 意味 |
| --- | --- |
| **x-client-transaction-id** | X の全 API リクエストに必要なヘッダ。ホームページの SVG アニメーション座標と `ondemand.s.js` のキーバイトから署名を生成する。ブラウザで JS を実行したことを証明させるアンチボット機構 |
| **operation ID** | GraphQL の persisted query ハッシュ。クエリ定義が変わると変わる |
| **fork network** | GitHub 上で Fork ボタンから派生したリポジトリの集合。上流が takedown されると全体が影響を受けうる |
| **yank** | PyPI でバージョンを「新規解決から除外するが既存の固定は壊さない」状態にすること。削除とは別 |
| **wheel** | Python のビルド済み配布形式（`.whl`）。sdist（ソース配布）と対になる |
